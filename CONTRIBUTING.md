# Contributing

Thanks for your interest in making BDO Assistant better.

## TL;DR

1. Fork the repository
2. Create a branch from `main` (`git checkout -b feat/my-thing`)
3. Make your changes
4. Run `npm test` and `npm run build` — both must pass
5. Open a PR against `main` with a clear description
6. Wait for review from the BDFL (see [GOVERNANCE.md](GOVERNANCE.md))

## What kinds of contributions are welcome

- **Bug fixes** that include a clear repro or a test
- **Refactors** that don't change behavior but improve readability / reduce complexity
- **Documentation improvements** (typos, clarifications, missing examples)
- **New test coverage** for existing code
- **Translations** of existing UI strings (must include all three languages OR clearly mark strings as `// TODO: translate`)
- **Performance improvements** with a benchmark

## What kinds of contributions are NOT accepted

These are **hard NOs** — PRs that do any of these will be closed without
detailed review:

- **Changing the license** away from MIT. The license is non-negotiable.
- **Adding telemetry, analytics, or any network call to a third party** that
  isn't the user themselves. The local-first promise is the entire point of the
  project.
- **Shipping scraped third-party content** in the installer or in the repo
  (e.g., dumping scraped data into `data/`). User data must be generated by
  the user.
- **Adding commercial / monetization features** (ads, premium tiers, etc.).
- **Branding that implies affiliation with Pearl Abyss, Kakao Games, or
  garmoth.com.** Naming the game is fine; *suggesting the project is official*
  is not.
- **Mass automated rewrites** (e.g., "I reformatted every file with prettier")
  that bury smaller changes in noise. Do targeted PRs.

## Style

There is no enforced formatter. Match the style of the file you're editing.

For code:

- TypeScript, CommonJS for the RAG, `module: none` for the renderer.
- Prefer small, focused PRs over big-bang changes.
- Tests are encouraged but not required for trivial changes (typos, docs).
- For non-trivial changes, **add or update a test**.

For i18n strings:

- Update **both** `TR` in `src/ui/renderer/renderer.ts` **and** `TRANSLATIONS`
  in `src/i18n/locales.ts`. Keys must be identical across locales.
- Use `dot.case` keys. No empty strings.
- If you don't speak all three languages, mark missing translations with
  `// TODO(en):` / `// TODO(pt):` and the maintainer will get them translated.

## PR checklist

- [ ] Code compiles: `npm run build` exits 0
- [ ] Tests pass: `npm test` shows 0 failures
- [ ] UI build works: `npm run build:ui`
- [ ] If you touched i18n, both `TR` and `TRANSLATIONS` are updated
- [ ] If you added a user-facing string, it goes through `t()` (renderer) or
  `TRANSLATIONS` (RAG)
- [ ] PR description explains **what** and **why**, not just "fixes #X"

## Reporting bugs

Use the [bug report template](.github/ISSUE_TEMPLATE/bug_report.md). Include:

- Steps to reproduce
- Expected vs. actual behavior
- OS / Node version / Ollama version / model versions
- Any relevant log output (scrape logs, console errors)

## Suggesting features

Use the [feature request template](.github/ISSUE_TEMPLATE/feature_request.md).
Proposals that require a server, account, or telemetry will be closed
immediately — see the project scope in [GOVERNANCE.md](GOVERNANCE.md).

## Security issues

**Do not open a public issue.** See [SECURITY.md](SECURITY.md) for the
disclosure policy.

## Community

Be patient. The BDFL has a day job. Reviews may take a few days. If your PR
sits without review for over a week, ping with a comment — no need to @ anyone
uncomfortably.

And follow the [Code of Conduct](CODE_OF_CONDUCT.md). It's the standard OSS
one; nothing surprising.
